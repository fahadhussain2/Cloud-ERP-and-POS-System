## Goal

**A salesman takes payment and the bill prints, offline, in one keystroke after the total:** `F9` and Enter for exact cash, a quick-cash click when the customer hands over more, or a reference for Raast, JazzCash, Easypaisa or card, or several methods on one bill (`Shift+F9`). The counter gives the bill its number, writes it with its outbox row **in one local transaction**, and only then prints it to the counter's default printer with its Code 39 bill code. A lost or jammed print is reprinted from the counter, marked REPRINT. Push to the server is next (W1-07).

## Design

| Choice | Why |
|---|---|
| **The rules live in `packages/domain`**, pure and golden-tested: rounding of the bill total, which tenders are valid, change, quick-cash amounts, the document number, the bill code, and `buildSaleDocument` (bill + payments + context → the finalized document). The worker allocates the sequence and calls the same function; the server re-checks with it in W1-07. | CLAUDE.md rule 2. The clock, ids and sequence are passed in, so the same input always gives the same document. |
| **Cash rounding applies to the bill total, whatever the tender** (POS-15, Q5): total = `roundCash(lines − bill discount, tenant.cash_rounding_increment)`, the difference is the document's `rounding` (posted to the rounding account in W1-08). Delux: Rs 1. The bill panel shows a *Rounding* row only when it isn't zero (in practice only fractional quantities make paisa, since prices are whole rupees, D-056). | One total per bill: the same figure on screen, on paper, in the bill code and in every payment. Rounding only the cash part would give a split bill two totals. |
| **Payment pad under the total** (POS-17, D-053, the prototype): *Cash `F9`* (large, accent), *Bank / Raast*, *JazzCash*, *Easypaisa*, *Card*, *On account*, *Split payment `Shift+F9`*. All disabled while the bill is empty; **pay is refused while a line still needs an approval** (*Approve the prices first*). *On account* stays disabled until a credit customer can be chosen (W1-09). The buttons come from the pulled `payment_methods` (active ones, in their `sort`), so a method the tenant switched off isn't shown. | The pad the owner reviewed. A bill can't be finalized with a price nobody approved (D-092). |
| **Cash popup:** the total in large green figures; *Cash received* (optional, whole rupees); the quick-cash buttons *Exact* plus the next three round amounts above the total (for each of 500, 1,000, 5,000 and 10,000, the next multiple strictly above the total; the three smallest distinct ones, topped up with further multiples of 5,000 when fewer than three; the prototype's rule, which gave only one amount for totals like Rs 9,800), each showing its change; the change in large figures. **Enter with the field empty = exact**; a quick-cash click finalizes at once. Less than the total is refused (*use Split payment*). | PRD W1 step 4, D-053. Quick cash only inside the popup, so no misclick on the main screen finalizes a bill. |
| **Non-cash popup:** the amount, one reference field with the method's own label (*Raast or IBFT ID*, *JazzCash transaction ID*, *Card slip or approval code*…), required when the method `requires_reference`, 1–40 characters. | PRD W3; the reference matches the payment with the bank later. |
| **Split popup (`Shift+F9`):** one row per method with an amount (cash prefilled with the total) and its reference; *Cash received* for the cash part; *Rs X still to cover* / *Fully covered*. Finalizes only when the amounts add up exactly to the total. **Every tender is reachable from the keyboard here** (a single method takes the whole amount); the single-method buttons are the mouse shortcut. | POS-03 (no mouse needed), POS-06. |
| **Tender rules** (`tender.ts`): each payment > 0 and in whole increments; at most one row per method; sum = total exactly; references where required; cash received ≥ the cash part and only with a cash part; change = received − cash part. **Cash due** = the cash part (what the salesman brings to the cash desk); `handover_status` is `pending` when it's above 0, else `not_applicable`. | Data model §5 (`sales_payments`, `cash_due`). Only cash goes through the handover (W3). |
| **Number:** `{device code}-S{seq:6}`, e.g. `C03-S000001`; the `S` series starts at 1 on each counter. **The finalize transaction** (worker, one SQLite transaction, data model §12): read and increment `local_series`, build the document, insert `local_documents` and the `outbox` row (`pending`), delete the person's `open_bills` row, commit. Any failure rolls everything back: no number is used, the open bill is still there. | POS-13, rule 6: gapless and never reused, because the number is only taken in the transaction that keeps the bill. |
| **A double Enter can't make two bills:** the finalize request names the open bill it pays; the transaction deletes that row, so a second request finds none and gets the first result back. | Two bills for one sale would need a manager void (W1-12). |
| **The sale document** (`SaleDocumentV1` in `@erp/contracts`, zod, fixed now so W1-07 can accept it): `version, id (UUIDv7), family 'S', seq, number, deviceId, branchId, kind 'sale', createdAt (device clock), businessDate (D-056 cutoff), sellerId, customerId null, walkinPhone null, tierId`; `lines` (`lineNo, itemId, qty` thousandths, `listPrice, floorPrice, unitPrice, lineDiscount, billShare, lineTotal`); `amounts` (`subtotal, lineDiscountTotal, billDiscount, rounding, taxTotal 0, total`); `payments` (`method` code, `amount, cashReceived, changeDue, reference`); `cashDue, handoverStatus`; `overrides` (each W1-05 approval: `kind, lineNo` or none for the bill, `requestedBy, approvedBy, reason, note, values, at`); `clientVersion`. Money as whole minor units, never floats (rule 1). | Data model §5, so the server stores it without guessing. The payload is what the device signs and what W1-07 validates. |
| **Signature:** right after the commit, the counter signs the canonical payload with its device key (`signCanonical`, D-082) and stores it on the outbox row. If that fails (it shouldn't), push signs any unsigned row before sending (W1-07). | The key lives in IndexedDB on the page, not in the SQLite worker, and signing never delays the bill. |
| **Then print** (data model §12: print after commit). The bill is an HTML/CSS page rendered into a print-only container and printed with `window.print()`; the counter runs Chrome/Edge with `--kiosk-printing`, so it goes silently to the default Windows printer (architecture §8). A failed or lost print doesn't touch the bill: it is already saved and can be reprinted. The salesman sees *Bill C03-S000412 printed · bring Rs 4,320 to the cash desk, change Rs 680* and a new empty bill. | POS-09, D-047. Print can't report paper jams; the reprint covers that. |
| **The printed bill** (POS-09, the prototype's layout, Q12): shop name and header lines (branch `receipt_header`, placeholders until the go-live checklist item), *SALE BILL*, bill number, date and time, counter, salesman, customer (*Walk-in*); lines (#, code, description, qty, rate, amount); subtotal, discount, rounding, **TOTAL**; each payment with its reference; *Cash received* and **CHANGE**; the policy line (*Exchange or return within 30 days with this bill*, from the print profile); the bill code with its text under it. Black on white, no shading, large figures. All text through i18n keys, laid out with logical properties (rule 10). | One template the owner already saw, for A5 landscape (D-055) and A4. |
| **Print profile** (POS-16, D-048): the device's `print_profile_id`, else the tenant default. Fields used: `paper_format` (a5: A5 landscape page; a4: A4 portrait page), `copies` (2 = a second page in the same print job), `code_type` (`barcode`), `template_options` (header lines, policy text). **Delux stays on A5 landscape** (D-055, owner answer 1); A4 is built too, so a different paper in the P1005 is a profile setting, not code. **Thermal 80/58 mm and the signed QR are not built now** (owner answer 2): no tenant uses them, and both stay possible without a schema change. | Build what Delux needs; the profile already carries the choice. |
| **Bill code** (architecture §4.5, D-055): Code 39 of `<bill number> <cash due in whole rupees>`, e.g. `C03-S000412 4320` (`C03-S000413 0` for a bill paid entirely by Raast). No check character. `billCode` / `parseBillCode` in `packages/domain`; the bars are SVG from a pure Code 39 encoder in a new `packages/print` (labels reuse it, CAT-08). | The cash desk records an offline handover from exactly these two facts (W1-10). SVG bars need no barcode font on the counter. |
| **Reprint** (POS-10): `Alt+P` opens *Reprint*: this counter's bills from `local_documents` (today first, up to 30 days), searchable by number, `↑ ↓` and Enter. The copy prints with a **REPRINT** band (time and who). Anyone unlocked may reprint, no PIN (owner answer 3); each reprint is kept in a new local `reprints` table and pushed for the audit log with W1-07, like `pin_events`. | A jammed shared printer must not stop the shop (PRD §10). A reprinted barcode can't collect cash twice: the handover is unique per bill (data model §6). |
| **New pull datasets** (sync spec §3): `payment_methods` (`id, code, name, is_cash, requires_reference, is_active, sort`; **not `bank_account_id`**), `print_profiles` (`id, name, paper_format, code_type, copies, template_options, is_tenant_default`), and `device` (this device's own row: `id, code, print_profile_id, status`). The tenant's `cash_rounding_increment` and `day_cutoff_hour` and the branch's `receipt_header` are already pulled. | The counter needs them offline; columns listed explicitly as for every dataset. |
| **Local schema 5:** `payment_methods`, `print_profiles`, `device` (pulled), `reprints` (`id` UUIDv7, `document_id, number, user_id, at, pushed_at`). An existing counter with open bills, PIN events and outbox rows upgrades in place (rule 9). | Data model §12. |
| **Keys** (POS spec §11): `F9` cash and `Shift+F9` split now show in the key bar; `Alt+P` reprint. In every popup: Enter = the main button (*Finalize & print*), Esc = cancel, Tab = next field (D-053). `F9`'s browser default is prevented like the other function keys. | The prototype's map; `Alt+P` is free in Chrome and Edge. |
| **No `/print-test` page:** W1-01's build parts (Code 39, the bill code, the bill layout) are built here for real; **W1-01 becomes only the hour at the shop**, printing real bills from a staging counter on the generated catalog (W1-21) and scanning them. | The go-live checklist already deferred W1-01 until real bills exist, and the printer turned out to be a laser (HP LaserJet P1005), so the dot-matrix speed risk that made it first is gone. |

## Scope

1. **`packages/domain`:** `rounding` of the bill total (`saleTotal`), `tender.ts` (`checkTender`, `cashChange`, `cashDue`, `quickCash`), `documentNumber`, `billCode` / `parseBillCode`, `sale-document.ts` (`buildSaleDocument`); golden files `sale-total.json`, `tender.json`, `quick-cash.json`, `document-number.json`, `bill-code.json`, `sale-document.json`.
2. **`packages/print`** (new): `encodeCode39(text)` → bar widths, `code39Svg(text, options)`; golden `code39.json`.
3. **`packages/contracts`:** `SaleDocumentV1` (zod) and the three new pull datasets' column lists.
4. **`apps/api`:** the three pull datasets (column-listed, `device` scoped to the calling device), with integration tests. No push or `sales_documents` yet (W1-07).
5. **`apps/pos`:**
   - local schema 5 and the worker messages `finalizeSale`, `setSignature`, `recentDocuments`, `recordReprint`; settings expose rounding increment, cutoff hour, header, payment methods and the print profile
   - the payment pad in `BillPanel`, the Cash, method and Split popups, `F9` / `Shift+F9`, the toast after finalize (`packages/ui`, from the shadcn CLI)
   - `print/`: the bill component (A5 landscape, A4), the print container, `printBill(document, profile, { reprint })`
   - the Reprint dialog (`Alt+P`)
6. **E2E** (`e2e/counter.spec.ts`, `window.print` stubbed to capture the printed bill): exact cash; cash with change by typing and by quick cash; less than the total refused; Raast with a reference (missing reference refused); split cash + JazzCash with cash received; pay refused while a price needs approval; numbers `S000001`, `S000002` survive a reload; the status bar's unsynced count goes up; offline finalize and print; reprint shows REPRINT.
7. **Docs:** POS spec §12 *Payment and finalize*, §13 *Printing and reprint* (drafted after acceptance, before code), §11 keys; sync spec §3 datasets and §6 (the document payload; push itself is W1-07, fixing *Push is added with W1-06*); data model §12 (schema 5); POS README; `infra/counter-setup.md` (default printer, A5 paper size, `--kiosk-printing` on the installed app's shortcut); WAVE-1-TASKS and the W1-01 plan (W1-01 = the shop hour, after this task); a decision entry (D-093) for the choices and owner answers.

**Out of scope:** push, server acceptance and exceptions (W1-07); posting and the rounding account (W1-08); customers, on account and credit limits (W1-09); the cash desk queue and scan (W1-10); hold and void (W1-12); returns, exchanges and refunds (W1-13); thermal templates and the signed QR (owner answer 2); the shop print test itself (W1-01).

## Risks

| Risk | Mitigation |
|---|---|
| The P1005's paper isn't what the template assumes (A5 sheets vs A4) | A5 landscape is the Delux default (owner answer 1); A4 is built and checked as a PDF too. The shop hour (W1-01) confirms the paper, and switching is a print-profile setting. |
| `window.print()` gives no error when the printer is off or jammed | The bill is saved before printing; *Reprint* (`Alt+P`) is one key away, and the toast names the bill number. |
| The sale document's shape is fixed before the server accepts it | It carries a `version`; W1-07 accepts v1, and any later version is added alongside (the server accepts the previous client version, architecture §4.2). |
| A crash between commit and signing leaves an unsigned outbox row | Push signs unsigned rows before sending (W1-07); the payload was already committed, so nothing is lost. |
| Two finalizes race (double Enter, a click and Enter) | The open bill row is the guard: deleted in the same transaction, so the second finds none (tested). |
| A rounding or tender edge case gives a split that never adds up | All amounts are integers through `add`/`sub`; golden cases at one paisa over and under. |

## Owner answers (2026-10-27)

1. **Paper:** keep **A5 landscape** as the Delux default, like the legacy bill (D-055); A4 is built as well. The paper actually in the HP LaserJet P1005 is confirmed at the shop hour (W1-01); if it is A4, the print profile is switched, with no code change.
2. **Thermal receipts and the signed QR** are built only when a tenant needs one. Delux keeps the unsigned Code 39 barcode: its bills print on the shop's own printer at the cash counter, and its scanners already read Code 39. An offline return of another counter's unsynced bill uses the no-receipt PIN flow (D-048).
3. **Reprint:** anyone unlocked on the counter may reprint, with no PIN; every copy is marked REPRINT (time and who) and logged for the audit log.
4. **Rounding:** the bill total is rounded to Rs 1 for every bill, whatever the tender, so the screen, the paper and every payment show one total.
