## Goal

**A customer brings back a part, with the bill or without it, and the salesman takes it back on one screen: marks what comes back with a reason and a condition, optionally adds the right part, and finalizes one document whose net is paid at the cash desk, refunded at the desk, credited to the account or settled even.** A part from a bill of this system is refunded at what the customer actually paid (D-005) and goes back into Shop or Damaged at its original cost (D-044); one without a bill of this system (lost, or bought before go-live) is a no-receipt return with a manager's PIN. The cash desk pays out from its queue or by scanning, as built in W1-10. It works offline (PRD principle 1), and nothing already printed is changed (rule 3).

## Design

| Choice | Why |
|---|---|
| **One document, signed quantities** (D-006, data model §5): a return or exchange is an `S` document like a sale, in the same series (POS-13): lines with a negative quantity come back, lines with a positive one are sold, and `kind` is derived (all positive `sale`, all negative `return`, mixed `exchange`). One number, one print, one cash movement. | Already decided; the server tables (0008) were built for it. |
| **`SaleDocumentV2`** (`@erp/contracts`, sync spec §6.1): V1 plus signed quantities, the return fields below, a total and cash due that may be negative, refund payments (negative amounts) and no payment for an even exchange. **Written only for a document with returned lines**; a plain sale stays V1, so the pilot's sales are untouched. Push accepts both (architecture §4.2). | V1 is strict (positive quantities, `kind: 'sale'`), so returns can't be additive to it. Keeping plain sales on V1 keeps this task out of the pilot's main path. |
| **A returned line** carries `qty` < 0; **`returnOf`**: `{ documentId, number, lineNo }` for a bill of this system, or null without a receipt; `reason`, `condition`, `note`; `unitPrice` = the refund per unit (shown and printed), `lineTotal` = −refund; `listPrice`, `floorPrice` null, `lineDiscount` and `billShare` 0. The document carries `returnOf: { id, number }` for the original bill, or `noReceipt: { ref }` (a bill number the customer or the manager gives, e.g. a legacy bill's, for the record). | Naming the original line by document id and line number works for a bill the server doesn't have yet (this counter's own unsynced bill): server line ids are made on the server. The return document can gain another kind of original in a later version without changing these. |
| **One original bill per return** (owner answer 2). The return's customer is the original bill's (fixed); without a receipt it is the one chosen (`F4`) or walk-in. Replacement items are then added from search like any sale, with every price, floor and approval rule (POS spec §10). A bill discount (`D`) applies to the sold lines only. | One customer per document, and a refund on account must go to the bill's own customer. Two bills = two returns, each with its own print. |
| **How much may come back, for how much** (`returnable` in `packages/domain`): per original line, **sold − returned so far**; the refund for `k` of the remaining `r` units is `round(remainingValue × k / r)` (half away from zero), where `remainingValue` = the line's net paid (`lineTotal − billShare`) minus what earlier returns refunded; returning all that is left refunds **exactly** what is left. So a line returned in parts always adds up to what the customer paid (PRD W6 step 4, posting rules §4.2). *Returned so far* = the server's returns of that line (pulled) and this counter's own returns the pull doesn't have yet. | Integer money only (rule 1); no rounding drift across partial returns. |
| **Finding the bill (`F3` *Return / exchange*)**: one search box: **scan the bill's code** (`C03-S000412 4320`), type a number (`C03-S000412` or `S412`), **a phone** (4 or more digits: the bills of customers with that phone, and walk-in bills with it, through `normalizePhone`), or **a date** (that day's bills). Results: number, date, counter, customer, total. Voided bills aren't listed; a bill older than the window is listed with *Outside the 30-day window*. The bill opens with each line: sold, already returned, returnable, refund per unit. Not found → *No receipt* (below). | PRD W6 step 1. Everything is local, so it works offline. |
| **Where the bills come from:** the branch's last 90 days pulled to every counter (below) and this counter's own documents (`local_documents`, so its unsynced bills too). An **unsynced bill of another counter** isn't known: the no-receipt flow, with its number as the reference (architecture §4.5, D-048). | SYN-01. |
| **Bills from before go-live are not in the system** (owner answer 4): the legacy bills aren't imported (MIG-03 dropped; D-030 in part superseded). Such a part is a **no-receipt return**: the salesman or manager looks the old bill up in the read-only legacy system, and the manager approves the refund price from it; the legacy bill number goes in `noReceipt.ref`. With the 30-day window this lasts about the first month after go-live. | Less code and data: no second kind of original in the lookup, the quantities, the review, the posting and the print, no importer step and no generated legacy bills, for a benefit of about a month. |
| **Marking lines:** `↑ ↓` line, the quantity to return (≤ returnable), a **reason** (*Wrong part, Unused option, Defective, Changed mind, Other* with a note; owner answer 3) and a **condition** (*Resellable* → Shop, *Defective* → Damaged; the reason *Defective* presets it). *Add to the bill (Enter)* puts the returned lines on the open bill (an open bill must be empty first: hold it, `F8`). The bill panel shows them in orange under *Returned from C03-S000412*, then the sold lines, then the net. | PRD W6 step 2; D-008: defective goes to the non-sellable DAMAGED location. |
| **The policy** (`checkReturn`): the window is the item's category `return_policy.window_days`, else the tenant's **`return_window_days`** (30, PRD Q3), counted from the original's business date to today's; a category with `returnable: false` is non-returnable (Delux: none). **Approvals on the same screen** (PLT-07, as for a price): **`return_permission`** when the seller lacks `pos.return.create` (D-051), **`return_outside_policy`** (`pos.return.outside_policy`) outside the window or for a non-returnable category, **`no_receipt_return`** (`pos.return.no_receipt`) without a receipt. One approver's own PIN covers every kind they hold; a reason from the approval list (owner answer 3). Each is an override on the document (the kinds exist since 0008). | PRD W6 steps 5–7, D-005, D-051. |
| **No receipt** (D-005, owner answer 4): the counter **suggests** a refund per unit: the **lowest net unit price the item sold for in the last 90 days** (`lowestPrice90`: the branch's bills, any tier, not voided, not returned lines), else the default tier's current price. **The approver may change it** (e.g. to the price on the old legacy bill); an item with neither needs a typed price. The `no_receipt_return` override keeps the suggested and the approved price. The cost back into stock is the current average (posting rules §4.2). | Right after go-live there are no 90 days of sales yet, so the suggestion is today's price, which may differ from what was paid before go-live. The manager sets it from the old bill; the override report (RPT-03, W1-20) shows every changed price by approver. |
| **Settling the net** (POS spec §12, POS-17, W7): the net = sold lines − bill discount − refunds, cash-rounded as every bill. **Net > 0:** the normal pad. **Net < 0** the pad switches to **Refund cash at desk** (`F9`; cash due < 0 → the desk's payout queue; the bill says *Refund due Rs 450, collect at the cash desk*), **Credit to account** (only with a customer with a customer account; preselected when the original was paid on account), and **Refund by transfer** (owner answer 1: a bank or wallet method, its reference, and the PIN of someone with `pos.override.approve`, as an override `refund_transfer`; it posts to that method's bank account). **Net 0:** *Finalize even exchange* (no payment). One refund method per document. Refund popups show the amount in orange (D-053). | PRD W7, D-007, D-047. |
| **Credit on the counter:** a refund to account is **not** subtracted from `unsynced` (POS spec §15) until the pulled balance has it; an exchange's on-account net is checked as usual. | Never loosens credit control offline. |
| **Finalize** is the W1-06 transaction unchanged (rule 6); the worker re-runs `returnable` and `checkReturn` inside it with what the counter holds, so two returns of the same line on this counter can't both pass. On a desk with an open session a cash refund gets its automatic payout in the same transaction (cash desk spec §7, built in W1-10). | One local transaction, as every document. |
| **The print:** *RETURN* or *EXCHANGE* instead of *SALE BILL*; the returned lines under *Returned from C03-S000412 (12 Nov 2026)* (or *No receipt*, with the reference if given) with their reason and condition; the sold lines; the net; *Refund due Rs 450, collect at the cash desk* or *Credited to account*; the bill code with its negative amount (`C03-S000415 -450`, built in W1-10). | PRD W7. |
| **The cash desk changes nothing:** the refund is in the queue in orange and paid out by Enter or a scan (CSH-04, W1-10). This task adds its first e2e on a real return. | Built in W1-10 for this. |
| **A return can be voided** under W1-12's rules unchanged (same device and day, before its payout, `pos.void` and a PIN); its reversal swaps its posting. A voided return isn't reissued: the salesman starts again with `F3`. | No new rule; reissuing returned lines would skip the return checks. |
| **The 90-day bills on every counter** (SYN-01, architecture §4.3): three pulled datasets, branch-scoped, business date within the last 90 days: **`bills`** (`sales_documents`: `id, number, device_id, kind, status, business_date, customer_party_id, walkin_phone, total, return_of_id`), **`bill_lines`** (`sales_lines`: `id, document_id, line_no, item_id, qty, unit_price, line_total, bill_share, original_line_id`) and **`bill_payments`** (`sales_payments`: `id, document_id, method_id, amount`). **Never** the payload, signature, cost, payments' references or the cash figures. The walk-in phone is personal data: pulled for the lookup, never logged or printed. The counter deletes rows older than 90 days at start-up. Empty at go-live, growing to about 13,000 bills (~50,000 rows), within the 60-second bootstrap rule (measured in Verify). | PRD SYN-01 and principle 1: returns work offline. The pulled return lines carry what has been returned already, so no derived table is needed. |
| **Push of a return** (sync spec §6.2): V2 through the same claim, signature, schema, device and reference checks. Then **`reviewReturn`** (`packages/domain`) judges it under the **original bill's per-bill lock** (the W1-10 lock, by number), so returns of the same line from two counters are judged one after the other against the server's own figures. **Never refused on business rules** (rule 7); findings are exceptions: | One trust path. A printed return with cash paid out is a fact. |
| — **`return_over_quantity`** (high): more than sold − returned, usually two counters offline (`details`: `sold`, `returnedBefore`, `qty`). | The over-returned goods may not exist. |
| — **`return_original_invalid`** (medium): the original isn't on the server, is voided, is of another item, or is itself a returned line (`details.cause`: `missing`, `voided`, `other_item`, `returned_line`). | |
| — **`return_price_mismatch`** (medium): a linked refund other than what `returnable` gives on the server's figures, or a no-receipt refund other than its approved price (`details.cause`: `linked`, `no_receipt`; with both figures). | A manager's changed no-receipt price is expected and not flagged: it is on the override. |
| — **`return_not_permitted`** (medium): an approval missing or from someone the server says lacks the permission (`details.cause`: `permission`, `outside_policy`, `no_receipt`). | Like `below_floor_no_override`. |
| **Server storage** (migration `0014_returns.sql`): on **`sales_documents`** `return_of_id`, `return_of_number`, `no_receipt`, `no_receipt_ref` (from the document, set once at push; no foreign key on `return_of_id`, the original may be missing); on **`sales_lines`** `original_line_id`, `return_reason_code`, `return_condition`, `return_note`, and `location_id` = the branch's **DAMAGED** location for a defective line; **`tenants.return_window_days`** (default 30, pulled in `tenant`); the override kind `refund_transfer` (owner answer 1); the four exception kinds. The app role never updates or deletes a line (rule 3); `schema.ts` mirrors it. | Data model §5 already names these fields, except the legacy ones, which go (owner answer 4). |
| **Posting** (`postSale`, posting rules §4.2, §4.3), in the accepting transaction: a returned line debits **`SALES_RETURNS`** at its refund; its stock comes back **at the original line's unit cost** read from that line's movement (D-044; a no-receipt line at the current average) into SHOP or DAMAGED, the average recomputed as a receipt (`averageAfterReceipt`); negative payments credit cash in transit, the customer (a negative party entry) or the bank. **An exchange is one entry**; only the net settles. A linked return whose original hasn't posted waits, and posts when it has (like a void, W1-12). The rebuild replays it. | Posting rules §4.2–§4.3; rule 4. §8's worked example becomes a golden case. |
| **Local schema 11:** `bills`, `bill_lines`, `bill_payments` with exactly the pulled columns (`RETURN_COLUMNS` in `@erp/contracts`), indexes on number, business date, customer, walk-in phone, item and original line; the open bill's JSON gains its returned lines and their source (an open or held bill from before reads as having none). A counter with open bills, held bills, outbox and quarantined rows upgrades in place (rule 9). | Data model §12 lists the 90-day bills. |

## Build notes

- **The tests came first** (the first commit): the domain goldens (`return-lines.json`, `return-policy.json`, `no-receipt-price.json`, `return-bill.json` for `addReturn`, `exchange-totals.json`, `refund-tender.json`, `return-document.json`, `return-review.json`) and the posting golden (`post-return.json`, with a check that every case balances). Push, the datasets, local schema 11, the worker and the screens are tested with their code.
- **A separate builder:** `buildReturnDocument` makes the V2 document and `buildSaleDocument` stays as it was for V1; the worker picks one by whether the open bill has returned lines. Every caller of the sale builder is unchanged. `AnySaleDocument` (V1 or V2) is what the counter stores, prints and voids.
- **The return's approval is given when its lines go on the bill** (the `F3` dialog, then the approval on the same screen), and kept on the bill's `returns` block; the returned lines can't be edited after (`Alt+C` clears the bill, `removeReturn` in the domain). A refund by transfer is approved at payment. So an approval never has to be judged again for a changed line.
- **A refund to account isn't credit:** `reviewCredit` and the push's credit check skip an on-account amount below 0, and the counter's `unsynced` counts only positive on-account parts.
- **`bill_lines` sends `line_total`** (already net of the bill discount) and not `bill_share`: what was paid is all a return needs.
- **A return waits for its original:** `waitingReturns` (`packages/posting`) finds returns whose original line is linked and unposted; push posts them right after their original, and `postPending` excludes them until then and posts them after the original in the same pass. The rebuild takes the original's replayed movement for the cost.
- **A line is linked to its original only when it can come back at its cost** (the same item, a sold line); otherwise it is stored unlinked (flagged `return_original_invalid`) and comes back at the current average.
- **The return dialog is one dialog for all its steps** (find, lines, no receipt): e2e showed that swapping dialogs moved the focus out of the new one, which then closed itself.
- **Known limit:** a bill with only returned lines can't be held (`F8` needs sold lines, `checkHold`); finish the return or clear it.
- **E2E covers** a handed-over bill returned and its refund paid out at the desk, an exchange, a no-receipt return approved by the manager, and an offline return of this counter's own bill. A part returned in two goes, a refund to account, out of the window, and a seller without `pos.return.create` are covered by the goldens, the worker tests, the integration tests and the screen tests rather than e2e.

## Risks

| Risk | Mitigation |
|---|---|
| Two counters return the same line while offline | The worker's check covers one counter; the server judges returns of a bill one at a time under its lock and flags `return_over_quantity` (high). |
| A bill of another counter that hasn't synced can't be found | The no-receipt flow with its number as the reference (architecture §4.5); a manager approves it. |
| A pre-go-live part is returned twice, or refunded at more than was paid, in the first month (no legacy bills, owner answer 4) | Every such return needs a manager's PIN, who checks the legacy system (which also shows its own returns); the legacy number is kept as the reference; the override report (RPT-03, W1-20) lists no-receipt returns and changed prices by approver. |
| Many manager PINs in January | Expected for about the 30-day window; the owner chose it over importing legacy bills (owner answer 4). |
| The 90-day datasets make the first pull too slow | Columns kept to the minimum; measured in Verify against the 60-second rule; if over, the bill lines are pulled after the catalog so selling starts first. |
| Salesmen refund at a higher price than paid | A linked refund comes from the original line, not typed; no-receipt needs a manager's PIN; the server flags a mismatch. |
| The task is longer than its 3 days | Built in order: returns of this system's bills with the refund, then exchange, then policy and no-receipt (owner answer 5). |

## Owner answers (2026-11-03)

The recommended option for questions 1–3 and 5; question 4 as the owner chose.

1. **Refunds to bank or wallet payers** (PRD W7: "a manager decides between a cash payout and a transfer"): the counter offers *Refund by transfer* with the method, a reference and the PIN of someone with `pos.override.approve`, recorded as an override of a new kind **`refund_transfer`**; it posts to that method's bank account.
2. **One original bill per return document:** returns from two bills are two documents. The customer is the original bill's and can't be changed.
3. **Reasons:** return reasons as the PRD: *Wrong part, Unused option, Defective, Changed mind, Other* (with a note). Approval reasons (permission, out of policy, no receipt, transfer): *Regular customer, Manufacturer defect, Lost bill, Bought before go-live, Owner's instruction, Other* (with a note).
4. **The legacy bills:** not imported. A part bought before go-live is a no-receipt return with a manager's PIN, who sets the refund price from the old bill in the legacy system. MIG-03 is dropped and D-030 superseded in that part (D-100, with the build).
5. **Size and order:** one task of about 4½ days, built in the order: returns of this system's bills with the refund → exchange → policy and no-receipt.
