## Goal

**A customer brings back a part, with the bill or without it, from this system or from the legacy system in the last 90 days, and the salesman takes it back on one screen: marks what comes back with a reason and a condition, optionally adds the right part, and finalizes one document whose net is paid at the cash desk, refunded at the desk, credited to the account or settled even.** The refund is what the customer actually paid (D-005); the part goes back into Shop or Damaged at its original cost (D-044); the cash desk pays out from its queue or by scanning, as built in W1-10. It works offline (PRD principle 1), and nothing already printed is changed (rule 3).

## Design

| Choice | Why |
|---|---|
| **One document, signed quantities** (D-006, data model §5): a return or exchange is an `S` document like a sale, in the same series (POS-13): lines with a negative quantity come back, lines with a positive one are sold, and `kind` is derived (all positive `sale`, all negative `return`, mixed `exchange`). One number, one print, one cash movement. | Already decided; the server tables (0008) were built for it. |
| **`SaleDocumentV2`** (`@erp/contracts`, sync spec §6.1): V1 plus signed quantities, the return fields below, a total and cash due that may be negative, refund payments (negative amounts) and no payment for an even exchange. **Written only for a document with returned lines**; a plain sale stays V1, so the pilot's sales are untouched. Push accepts both (architecture §4.2). | V1 is strict (positive quantities, `kind: 'sale'`), so returns can't be additive to it. Keeping plain sales on V1 keeps this task out of the pilot's main path. |
| **A returned line** carries `qty` < 0; **`returnOf`**: `{ documentId, number, lineNo }` for a bill of this system, `{ legacyLineId, legacyNumber }` for a legacy bill, or null without a receipt; `reason`, `condition`, `note`; `unitPrice` = the refund per unit (shown and printed), `lineTotal` = −refund; `listPrice`, `floorPrice` null, `lineDiscount` and `billShare` 0. The document carries `returnOf: { id, number }` or `legacyReturnOf: { id, number, date }` for the original bill, or `noReceipt: { ref }` (the number the customer remembers, if any). | Naming the original line by document id and line number works for a bill the server doesn't have yet (this counter's own unsynced bill): server line ids are made on the server. |
| **One original bill per return** (owner question 2). The return's customer is the original bill's (fixed); without a receipt it is the one chosen (`F4`) or walk-in. Replacement items are then added from search like any sale, with every price, floor and approval rule (POS spec §10). A bill discount (`D`) applies to the sold lines only. | The data model has one `legacy_sale_id` and one customer per document, and a refund on account must go to the bill's own customer. Two bills = two returns, each with its own print. |
| **How much may come back, for how much** (`returnable` in `packages/domain`): per original line, **sold − returned so far**; the refund for `k` of the remaining `r` units is `round(remainingValue × k / r)` (half away from zero), where `remainingValue` = the line's net paid (`lineTotal − billShare`) minus what earlier returns refunded; returning all that is left refunds **exactly** what is left. So a line returned in parts always adds up to what the customer paid (PRD W6 step 4, posting rules §4.2). *Returned so far* = the server's returns of that line (pulled), this counter's own returns the pull doesn't have yet, and for a legacy line its `returned_qty`. | Integer money only (rule 1); no rounding drift across partial returns. |
| **Finding the bill (`F3` *Return / exchange*)**: one search box: **scan the bill's code** (`C03-S000412 4320`), type a number (`C03-S000412`, `S412`, or a legacy number, shown with its date because legacy numbers restart per period, migration doc §5), **a phone** (4 or more digits: the bills of customers with that phone, and walk-in bills with it, through `normalizePhone`), or **a date** (that day's bills). Results: number, date, counter, customer, total, *Legacy*. Voided bills aren't listed; a bill older than the window is listed with *Outside the 30-day window*. The bill opens with each line: sold, already returned, returnable, refund per unit. Not found → *No receipt* (below). | PRD W6 step 1. Everything is local, so it works offline. |
| **Where the bills come from:** the branch's last 90 days pulled to every counter (below), this counter's own documents (`local_documents`, so its unsynced bills too), and the legacy bills. An **unsynced bill of another counter** isn't known: the no-receipt flow, with its number as the reference (architecture §4.5, D-048). | SYN-01. |
| **Marking lines:** `↑ ↓` line, the quantity to return (≤ returnable), a **reason** (*Wrong part, Unused option, Defective, Changed mind, Other* with a note; owner question 3) and a **condition** (*Resellable* → Shop, *Defective* → Damaged; the reason *Defective* presets it). *Add to the bill (Enter)* puts the returned lines on the open bill (an open bill must be empty first: hold it, `F8`). The bill panel shows them in orange under *Returned from C03-S000412*, then the sold lines, then the net. | PRD W6 step 2; D-008: defective goes to the non-sellable DAMAGED location. |
| **The policy** (`checkReturn`): the window is the item's category `return_policy.window_days`, else the tenant's **`return_window_days`** (30, PRD Q3), counted from the original's business date to today's; a category with `returnable: false` is non-returnable (Delux: none). **Approvals on the same screen** (PLT-07, as for a price): **`return_permission`** when the seller lacks `pos.return.create` (D-051), **`return_outside_policy`** (`pos.return.outside_policy`) outside the window or for a non-returnable category, **`no_receipt_return`** (`pos.return.no_receipt`) without a receipt. One approver's own PIN covers every kind they hold; a reason from the approval list (owner question 3). Each is an override on the document (the kinds exist since 0008). | PRD W6 steps 5–7, D-005, D-051. |
| **No receipt** (D-005): the refund per unit is the **lowest net unit price the item sold for in the last 90 days** (`lowestPrice90`: the branch's bills and the legacy bills, any tier, not voided, not returned lines), else the default tier's current price; an item with neither needs a typed price, within the same approval. The cost back into stock is the current average (posting rules §4.2). | PRD W6 step 5. The counter holds the 90 days, so the price is the same offline. |
| **Settling the net** (POS spec §12, POS-17, W7): the net = sold lines − bill discount − refunds, cash-rounded as every bill. **Net > 0:** the normal pad. **Net < 0** the pad switches to **Refund cash at desk** (`F9`; cash due < 0 → the desk's payout queue; the bill says *Refund due Rs 450, collect at the cash desk*), **Credit to account** (only with a customer with a customer account; preselected when the original was paid on account), and **Refund by transfer** (owner question 1). **Net 0:** *Finalize even exchange* (no payment). One refund method per document. Refund popups show the amount in orange (D-053). A legacy bill with a customer refunds to their account by default, one without in cash (owner question 4). | PRD W7, D-007, D-047. |
| **Credit on the counter:** a refund to account is **not** subtracted from `unsynced` (POS spec §15) until the pulled balance has it; an exchange's on-account net is checked as usual. | Never loosens credit control offline. |
| **Finalize** is the W1-06 transaction unchanged (rule 6); the worker re-runs `returnable` and `checkReturn` inside it with what the counter holds, so two returns of the same line on this counter can't both pass. On a desk with an open session a cash refund gets its automatic payout in the same transaction (cash desk spec §7, built in W1-10). | One local transaction, as every document. |
| **The print:** *RETURN* or *EXCHANGE* instead of *SALE BILL*; the returned lines under *Returned from C03-S000412 (12 Nov 2026)* (or *legacy bill 023956*, or *No receipt*) with their reason and condition; the sold lines; the net; *Refund due Rs 450, collect at the cash desk* or *Credited to account*; the bill code with its negative amount (`C03-S000415 -450`, built in W1-10). | PRD W7. |
| **The cash desk changes nothing:** the refund is in the queue in orange and paid out by Enter or a scan (CSH-04, W1-10). This task adds its first e2e on a real return. | Built in W1-10 for this. |
| **A return can be voided** under W1-12's rules unchanged (same device and day, before its payout, `pos.void` and a PIN); its reversal swaps its posting. A voided return isn't reissued: the salesman starts again with `F3`. | No new rule; reissuing returned lines would skip the return checks. |
| **The 90-day bills on every counter** (SYN-01, architecture §4.3): five pulled datasets, branch-scoped, business date within the last 90 days: **`bills`** (`sales_documents`: `id, number, device_id, kind, status, business_date, customer_party_id, walkin_phone, total, return_of_id, legacy_sale_id`), **`bill_lines`** (`sales_lines`: `id, document_id, line_no, item_id, qty, unit_price, line_total, bill_share, original_line_id, legacy_line_id`), **`bill_payments`** (`sales_payments`: `id, document_id, method_id, amount`), **`legacy_bills`** (`id, legacy_number, legacy_period, date, customer_party_id, total`) and **`legacy_bill_lines`** (`id, legacy_sale_id, item_id, qty, net_amount, returned_qty`). **Never** the payload, signature, cost, payments' references or the cash figures. The walk-in phone is personal data: pulled for the lookup, never logged or printed. The counter deletes rows older than 90 days at start-up. About 13,000 bills (~80,000 rows at go-live with the legacy ones), within the 60-second bootstrap rule (measured in Verify). | PRD SYN-01 and principle 1: returns work offline. The pulled return lines carry what has been returned already, so no derived table is needed. |
| **Push of a return** (sync spec §6.2): V2 through the same claim, signature, schema, device and reference checks. Then **`reviewReturn`** (`packages/domain`) judges it under the **original bill's per-bill lock** (the W1-10 lock, by number), so returns of the same line from two counters are judged one after the other against the server's own figures. **Never refused on business rules** (rule 7); findings are exceptions: | One trust path. A printed return with cash paid out is a fact. |
| — **`return_over_quantity`** (high): more than sold − returned, usually two counters offline (`details`: `sold`, `returnedBefore`, `qty`). | The over-returned goods may not exist. |
| — **`return_original_invalid`** (medium): the original isn't on the server, is voided, is of another item, or is itself a returned line (`details.cause`: `missing`, `voided`, `other_item`, `returned_line`). | |
| — **`return_price_mismatch`** (medium): a linked refund other than what `returnable` gives on the server's figures; or a no-receipt refund above the server's lowest 90-day price (`details.cause`: `linked`, `no_receipt`; with both figures). | A counter missing another counter's bills may compute a higher lowest price. |
| — **`return_not_permitted`** (medium): an approval missing or from someone the server says lacks the permission (`details.cause`: `permission`, `outside_policy`, `no_receipt`). | Like `below_floor_no_override`. |
| **Server storage** (migration `0014_returns.sql`): on **`sales_documents`** `return_of_id`, `return_of_number`, `legacy_sale_id`, `no_receipt`, `no_receipt_ref` (from the document, set once at push; no foreign key on `return_of_id`, the original may be missing); on **`sales_lines`** `original_line_id`, `legacy_line_id`, `return_reason_code`, `return_condition`, `return_note`, and `location_id` = the branch's **DAMAGED** location for a defective line; **`legacy_sales`**, **`legacy_sale_lines`** (data model §5; `legacy jsonb` with the original keys, `net_amount`, `returned_qty`); **`tenants.return_window_days`** (default 30, pulled in `tenant`); the four exception kinds. New tables: `tenant_id` + forced RLS, `enable_sync`, mirrored in `schema.ts`; the app role never updates or deletes a line (rule 3). | Data model §5 already names these fields. |
| **Posting** (`postSale`, posting rules §4.2, §4.3), in the accepting transaction: a returned line debits **`SALES_RETURNS`** at its refund; its stock comes back **at the original line's unit cost** read from that line's movement (D-044; a legacy or no-receipt line at the current average) into SHOP or DAMAGED, the average recomputed as a receipt (`averageAfterReceipt`); negative payments credit cash in transit, the customer (a negative party entry) or the bank. **An exchange is one entry**; only the net settles. A linked return whose original hasn't posted waits, and posts when it has (like a void, W1-12). The rebuild replays it. | Posting rules §4.2–§4.3; rule 4. §8's worked example becomes a golden case. |
| **Legacy bills** (MIG-03, migration doc §5): a new importer step (`pnpm legacy:import --label <label> --bills --since <date>`, on the owner's PC, D-084) reads the staged legacy sale headers, lines and sale returns and loads `legacy_sales` / `legacy_sale_lines`: items by code (`ItemID` = item code), the customer by partner code (`0002 CASH SALE` = walk-in), **each line's net** after the bill's discount (largest remainder, as `allocate`), and **`returned_qty`** from the legacy returns in the window (by their free-text bill reference where it parses, else reported). Idempotent by the legacy keys; `--dry-run` reports only. **Report:** count and Σ totals against the legacy Daily Sales Register (migration doc §8), unmatched items and unparsed return references; never phones or names. The final load is part of the cutover run (`--since` = cutover − 90 days). **Staging and e2e get generated legacy bills** from the generated catalog (`erp-tenant seed-catalog`, D-076), never real ones. | MIG-03. The real table names come from the staging report (owner question 4): this container can't read the dump (rule 11). |
| **Local schema 11:** `bills`, `bill_lines`, `bill_payments`, `legacy_bills`, `legacy_bill_lines` with exactly the pulled columns (`RETURN_COLUMNS` in `@erp/contracts`), indexes on number, business date, customer, walk-in phone, item and original line; the open bill's JSON gains its returned lines and their source (an open or held bill from before reads as having none). A counter with open bills, held bills, outbox and quarantined rows upgrades in place (rule 9). | Data model §12 lists the 90-day bills. |

## Risks

| Risk | Mitigation |
|---|---|
| Two counters return the same line while offline | The worker's check covers one counter; the server judges returns of a bill one at a time under its lock and flags `return_over_quantity` (high). |
| A bill of another counter that hasn't synced can't be found | The no-receipt flow with its number as the reference (architecture §4.5); the lowest 90-day price protects the shop. |
| The 90-day datasets make the first pull too slow | Columns kept to the minimum; measured in Verify against the 60-second rule; if over, the bill lines are pulled after the catalog so selling starts first. |
| The legacy sale tables or their bill-discount and return links are not what the migration doc assumes | Owner question 4 before building that part; the importer reports what it can't match and never guesses (D-085). It is built last, so the rest doesn't wait for the dump. |
| Salesmen refund at a higher price than paid | The refund comes from the original line, not typed; no-receipt needs a manager's PIN at the lowest price; the server flags a mismatch. |
| The task is twice its 3 days | Built in order: returns of this system's bills with the refund, then exchange, then policy and no-receipt, then legacy bills (owner question 5). |
