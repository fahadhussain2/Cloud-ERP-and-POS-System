## Goal

**Every finalized bill reaches the server by itself, exactly once, and nothing is ever lost.** When the counter is online a bill is pushed the moment it is saved; when it's offline the outbox waits and empties on its own when the internet comes back, in sequence order, with no button to press. The server **accepts every completed sale** (SYN-03) and records what looks wrong as an exception for review; it refuses only malformed, unauthenticated or tampered documents, and those wait on the counter under *Needs attention*, never dropped. A missing number is noticed and re-sent, and after a server restore the counters put back their last 30 days on their own (SYN-05). A back-office change reaches the counters within seconds through an SSE nudge (SYN-04). The counter warns when it has been out of touch too long (SYN-06) and shows its health on one page, which the back office also sees for every counter (PLT-09).

## Design

| Choice | Why |
|---|---|
| **Push** `POST /api/sync/push` (device token), body `{ clientVersion, schemaVersion, deviceClock, health, documents: [{ id, family, seq, payload, signature }], events: [...] }`, **at most 100 documents in `seq` order** per family → `200 { serverTime, results: [{ id, status: accepted \| duplicate \| rejected, exceptions: [kind], error? }], series: [{ family, through, missing: [[from, to]] }] }`. Zod schemas `PushRequest` / `PushResponse` in `@erp/contracts`. `400` only when the request itself is malformed (not one document), `401` for the token (sync spec §1). | Architecture §5.2, under `/api` like pull. One call carries the documents, the audit events and the health snapshot, so a counter that comes back online does one round trip. |
| **Per document, one database transaction** (architecture §5.2): claim the id in `sync_inbox` (`INSERT … ON CONFLICT DO NOTHING`, so two pushes of the same id can't both insert) → if already accepted: same payload hash = `duplicate` with the stored result, a different hash = `rejected: id_conflict` → verify the signature with **the document's own device's** public key → parse with `SaleDocumentV1` (version picked by `version`; v1 stays accepted when v2 arrives, architecture §4.2) → check that its device, branch, seller, tier, items and payment methods belong to this tenant → **re-check the rules** (`reviewSale`, below) → insert `sales_documents`, `sales_lines`, `sales_payments`, `overrides` and the `exceptions` → update the device's series → commit. A failure inside rolls back that document only; the others in the batch carry on. | Rules 3, 5 and 7. One bad document must never hold back the rest of the day's bills. |
| **Rejected only when** the payload can't be trusted or stored: `unsigned`, `bad_signature` (also written as a `bad_signature` exception, severity high), `bad_schema` (incl. an unknown `version`), `id_conflict`, `seq_conflict` (another id already holds this device's family and seq), `unknown_reference` (an id that isn't this tenant's), `wrong_device` (a document from another branch's device). **Everything else is accepted** (SYN-03, D-011). A rejected id isn't final: once the counter fixes it (e.g. signs it), the same id is checked again. | A sale the customer already walked out with is a fact. Rejecting means the server can't store it honestly; quarantine on the counter keeps it until someone looks. |
| **The server re-check** is `reviewSale(document, context)` in `packages/domain`, pure and golden-tested, built from the W1-05 and W1-06 functions (`priceNeed`, `canApprove`, `saleTotal`, `checkTender`, `businessDate`, `documentNumber`). Context: the tenant's rounding increment, time zone and cutoff; the device code; the seller's and each approver's roles **as the server knows them**. It returns exceptions, never throws: **`below_floor_no_override`** (a line below its floor, or without a list price, and no approval from someone with `pos.price.below_floor`); **`discount_over_limit`** (past the seller's limit with no approval by someone whose `pos.override.approve` limit covers it); **`document_inconsistent`** (lines, amounts, rounding, payments, cash due, number or business date don't add up; `details.code` says which, owner answer 2). Prices and floors are judged on the **document's own snapshot** (`listPrice`, `floorPrice`): a price changed in the back office during an outage is expected and not flagged (architecture §4.7). | Rule 2: the counter and the server run the same functions. Approvals are re-checked against the server's roles, so a counter with a stale or tampered role list is caught. |
| **Other exceptions** written on accept: **`clock_skew`** when `serverTime − deviceClock` is over 5 minutes either way (once per device per business day, architecture §4.4); **`revoked_device_doc`** for a document made by a device after it was revoked (owner answer 3); **`seq_gap`** (below). `exceptions` follows data model §10, with the three new kinds added there. The report that lists them is RPT-10 (W1-20). | The exceptions report needs them from the first pilot day; the screen can come later. |
| **Sequence gaps** (architecture §5.2): per device and family, `device_series` keeps `through` (every seq from 1 to it has arrived) and `max_seq`. A document above `through + 1` opens a row in `sequence_gaps` (`from_seq`, `to_seq`, `opened_at`, `resolved_at`) and a `seq_gap` exception; documents that fill it shrink or resolve it. Every push answer lists `series` with `through` and the missing ranges, so **the counter re-sends what's missing from its `local_documents`** without being asked twice. A rejected document counts as arrived (it is in `sync_inbox`); it isn't a gap but a quarantine. | Push is in seq order and rows leave the outbox only after an ack, so a real gap means the server lost something (a restore) or a bug. It must be loud. |
| **Re-push after a restore** (SYN-05): the counter keeps `pushed_through` per family in `sync_state` (the highest seq it got an ack for). When a push answer shows `through` below it, or missing ranges, the counter **puts those documents back in the outbox** from `local_documents` (with their stored payload and signature), at most 30 days back, and pushes them like any other. Idempotency (rule 7) makes this safe to repeat. On start-up the counter sends an empty push (the handshake: health and series), so a restore is noticed even on a quiet counter. | Architecture §5.4: everything after the restore point comes back from the counters, automatically. |
| **The counter's push loop** (`apps/pos/src/sync/push.ts`, like `pull.ts`): **right after every finalize** when online (the bill reaches the server, and from W1-10 the cash queue, in seconds: SYN-02, D-047); at start-up; when the network comes back; and every 60 s while the outbox isn't empty. One push at a time; batches of 100 until empty. Unsigned rows are signed first (W1-06). A failure (offline, 5xx) retries with **exponential backoff with jitter** (2 s doubling to 5 min); the next finalize or reconnect tries at once. `accepted` / `duplicate` → the outbox row is **deleted** in the same local transaction that raises `pushed_through`; `rejected` → `quarantined` with the error, never deleted (rule 9 still counts it); a 401 renews the token once, as pull does. | Architecture §5.2 and the sync skill's invariants. *Sent* and *removed* are the same moment, so a crash can only re-send, never lose. |
| **Audit events in the same push:** `pin_events` (`pin.locked`, `pin.unlocked_by_manager`) and `reprints` (`bill.reprinted`) go in `events`, each with its device-made UUIDv7 as the `audit_log` id (`ON CONFLICT DO NOTHING`, so re-sends are harmless), with the device and the users; the counter sets `pushed_at` on the answer. | Promised by W1-04 and W1-06 (sync spec §5, POS spec §13). |
| **Server tables (migration 0008):** `sales_documents`, `sales_lines`, `sales_payments`, `overrides` as data model §5 (money `bigint`, quantity `numeric(14,3)`, rule 1), plus the signed `payload` (jsonb), `payload_hash`, `signature`, `received_at`, `exception_count`; lines get the branch's SHOP location; `unit_cost` stays empty until posting. `sync_inbox`, `exceptions` (data model §10), `device_series`, `sequence_gaps`, `device_status`. Every table: `tenant_id` + forced RLS (rule 5); the sales tables also `enable_sync` and `enable_audit` (the cash queue and the 90-day bills pull them in W1-10 and W1-13); mirrored in `schema.ts`. The app role may not update or delete lines, payments or overrides (rule 3). | Data model §5 and §10, so the server stores the document without guessing. |
| **No posting yet:** W1-07 stores the document; **W1-08 adds posting to the same transaction** and posts every accepted document that has no postings yet (posting is derived and rebuildable, rule 4), so bills accepted on staging before W1-08 aren't left out. | Keeps this task to sync; the pilot (1 Dec) starts after W1-08. |
| **SSE nudge** (SYN-04): `GET /api/sync/events` (device token) streams `changes-available` after any commit to a pulled table of the device's tenant, and a comment every 25 s to keep proxies open. A trigger on each pulled table does `pg_notify('erp_sync', tenant_id)` (PostgreSQL folds repeats in one transaction, so a 125k-row import is one notice); the API holds one `LISTEN` connection and fans out to that tenant's streams, at most once per 2 s. The counter reads it with `fetch` (EventSource can't send the `Authorization` header) and pulls on each event; the stream closes when the 15-minute token expires and reconnects with a new one. **Polling drops to every 5 minutes while the stream is up**, and stays at 60 s without it. Caddy gets `flush_interval -1` on that path. `queue-changed` for the cash desk is added on the same stream in W1-10. | Architecture §5.3. No Redis, no new service (D-087); one API process today, and `LISTEN` keeps working if there are more later. |
| **Offline warnings** (SYN-06, POS-14): the counter keeps **`last_contact_at`** (the last successful push or pull) in `sync_state`, so a reload doesn't reset the clock. The status bar keeps *Offline since HH:MM* (red after 30 minutes); past **`offline_warning_hours`** (default 8) a banner under the status bar: *This counter hasn't reached the server for 8 hours. Bills are safe here and will sync when the internet is back*; past **`offline_strong_warning_hours`** (default 48) it turns red: *…for 2 days. Tell the manager.* **Selling is never blocked.** Both are new `tenants` columns, sent in the `tenant` dataset (owner answer 1). | PRD SYN-06 and the 8-hour pilot drill. Time since contact, not since the network dropped: a counter on Wi-Fi that can't reach the server is just as cut off. |
| **Device health on the counter** (PLT-09, architecture §11.3): one page, opened by clicking the status bar's sync area (and `Alt+S`, checked free in Chrome and Edge during the build): app and schema version; storage persisted, used and quota (`navigator.storage.estimate()`); online, last pull, last push, last contact; the server clock difference; bills waiting and the oldest one's age; PIN events and reprints waiting; **Needs attention**: quarantined bills with their error. *Try again* on a quarantined bill needs a manager (`admin.devices`, PIN) (owner answer 4). Works offline. | What a manager needs to answer "is this counter OK?" without calling anyone. |
| **Device health on the server:** every push (including the handshake) upserts `device_status`: last seen, last push, last pull (set by pull), client and schema version, unsynced count and oldest, quarantined count, storage persisted and usage, clock skew. The back office **Counters** screen (`admin.devices`) gains these columns: *Last seen*, *Waiting* (amber when the oldest is over 10 minutes, red over 4 hours), *App*, *Clock* (red over 5 minutes), *Storage* (red when not persisted), *Gaps* (open sequence gaps). | The owner sees every counter in one place (architecture §11.5 *Devices*). Grafana alerts on these numbers are a devops follow-up, not this task. |
| **Revoked counter** (owner answer 3): a refused token now says **`device_revoked`** (not a plain 401), and the counter stops with *This counter was removed in the back office. N bills on it haven't reached the server: don't clear this PC, call the manager.* Its data stays (rule 9). The back office gets **Re-enable** on a revoked counter (`admin.devices`, audited); after it, the counter gets tokens again and pushes. Documents created after the revocation time are accepted and flagged `revoked_device_doc`. | Architecture §4.3: a revoked device's documents are still accepted, flagged. Re-enabling is the shortest safe path for a counter revoked by mistake; a stolen one simply stays revoked. |
| **Logs** (architecture §11.2): each document's result is logged with the device, document id, number and exception kinds; each push with batch size, duration and counts. The counter's `diagnostic_log` keeps each push attempt. Never logged: tokens, signatures, PIN data (§11.7). | Trace a bill (W1-20) and the *API & sync* dashboard read these. |
| **Local schema 6:** `local_documents` gains `signature` (kept when the outbox row is deleted, for re-push) and an index on `(family, seq)`; `sync_state` keys `pushed_through:<family>`, `last_push_at`, `last_contact_at`, `server_clock_offset_ms`. A schema-5 counter with open bills, outbox rows, PIN events and reprints upgrades in place (rule 9). Bills older than 30 days are pruned from `local_documents`, **never one still in the outbox**. | Data model §12; SYN-01 says 30 days. |

## Build notes (2026-10-28)

- **Server re-check:** four golden cases were added while reaching 100% coverage: a bill discount larger than the lines (an `amounts` and a `rounding` finding, no price check on it), an approver the server doesn't know, and approvals naming a line that isn't on the bill. `SaleDocumentV1` now refuses an override whose values don't match it (a line's price, or the bill discount), which the re-check relies on.
- **A device pushes only its own documents.** A document is verified with the key of the device it names: well signed by another device → `wrong_device`, otherwise `bad_signature`. Carrying a re-enrolled PC's old documents is not built (owner answer 3).
- **The bill number isn't unique on its own:** `(device, seq)` is. A number that doesn't follow from them is accepted and flagged (`document_inconsistent`), so a unique index on it could have refused a sale.
- **Re-enable keeps the revocation window:** `devices` gains `last_revoked_at`, `reenabled_at` and `reenabled_by_user_id`; a document created between the two is `revoked_device_doc`. The `device_revoked` answer comes from the challenge call (revoking deletes the tokens, so a push with an old token is a plain `401`).
- **Clock skew** is recorded with the device's health, once per device and business day, not in each document's result.
- **Audit events** use the existing entity names (`users`, `sales_documents`), with the counter's time as `at`.
- **The change feed** (`createChangeFeed` in `packages/db`) opens its `LISTEN` connection with the first stream and reconnects after 5 s if it drops; the stream closes after 15 minutes, the token's life.
- **The counter (2026-10-28):** the push scheduler lives in the app shell: a push at start-up (the handshake), after every finalize, on reconnect and with the minute timer, which also pulls (every 5 minutes instead while the SSE nudge is up). The health page is a dialog over any screen (the sync figures in the status bar, or `Alt+S`); *Try again* uses the approval PIN check with `admin.devices` (`checkManager`). A revoked counter shows its own stop screen with the bills it still holds; *Check again* reloads.
- **The device token is fetched once for callers asking together:** pull, push and the SSE stream start at the same moment, and three challenges per start hit the 30-a-minute limit in the E2E run. A busy (429) or failing (5xx) token call is now treated like being offline (retried), not as a refusal.
- **Existing E2E flows changed:** online bills now reach the server at once, so two assertions of *N bills waiting to sync* became *0* (within 5 s), the Raast and split flow waits for its bills too, and the offline flow now expects 1, its own bill. Not yet checked in a real browser: that `Alt+S` reaches the page in the installed app.
- **Back office (2026-10-28):** the Counters list shows each counter as of its last contact: *Last seen*, *Waiting* (amber after 10 minutes, red after 4 hours, plus the refused bills), *App*, *Clock* (red over 5 minutes), *Storage*, *Missing bills*; a revoked counter has *Re-enable*, confirmed in a dialog. Caddy serves `/api/sync/events` on its own route, flushed at once and never compressed (`encode` moved to the other routes); `caddy validate` passes with 2.11.7.
- **The server corrects the reported health by what the push delivered:** the counter reports its outbox as it was before sending, so the server subtracts the bills it just accepted (and clears the oldest when none are left) and adds the ones it refused. Found by the E2E run, where a restore re-push left *11 waiting* on the Counters list.
- **E2E (`e2e/sync.spec.ts`):** the clock flow runs last and puts the clock back, because Playwright's clock stays on the whole browser profile once installed. A flow waits for *Last sync* before trusting *0 bills waiting* (the status bar shows 0 before the counter has read its outbox).

## Risks

| Risk | Mitigation |
|---|---|
| Four days is tight for push, gaps, restore, SSE, warnings and two health screens | **Everything stays in this task** (owner answer 5: the SSE nudge and the back-office health columns are kept). Built in that order, so push, gaps and restore, the pilot's must-haves (D-090), land first; if the task runs over, I say so as soon as I see it. |
| A bug in `reviewSale` flags good bills, or a bug in the server rejects them | The re-check never rejects (only exceptions); rejection is limited to the seven trust reasons, each tested; rejected bills stay on the counter under *Needs attention* and are re-tried after a fix. |
| Re-push after a restore re-queues thousands of bills at once | Batches of 100, one push at a time; duplicates are cheap (inbox lookup). Measured in Verify 2. |
| A counter's `pushed_through` is ahead of the server for another reason (a bug), causing endless re-pushes | Re-queue only documents the server lists as missing or above its `through`; each re-pushed one becomes `accepted` or `duplicate`, after which `through` catches up. Logged, and tested with a fake API. |
| SSE through Caddy buffers or times out | `flush_interval -1`, 25 s keep-alive comments, reconnect on close; the 5-minute poll still runs while the stream is up. Checked on staging. |
| `pg_notify` on large imports or catalog edits | One notice per transaction per tenant (PostgreSQL folds duplicates); the fan-out is limited to once per 2 s. |
| A server restored to before a counter enrolled doesn't know the device | Restore drills keep RPO ≤ 5 min (D-076), so this means a counter enrolled in the last minutes; it re-enrolls. Written in the restore runbook. |
