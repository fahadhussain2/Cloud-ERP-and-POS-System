## Goal

**Every accepted bill is in the books the moment it reaches the server, and the books can be proven from the bills.** In the same transaction that accepts a sale, the server writes its stock movement out of SHOP at the item's average cost, its journal entry (sales, discount, rounding, each tender's account, COGS against inventory), and, for a sale on account, the customer's ledger entry. Every entry balances (the database refuses one that doesn't). Stock may go negative, which never blocks anything and raises an alert (INV-03). If a bill can't be posted (an unmapped payment method, a bug), the sale is still accepted (SYN-03) and waits, flagged, until a job posts it. A **rebuild check** replays every posting from the documents and must match the live ledgers row for row (ACC-02, rule 4). No screens: the ledgers are read by W1-09 (customer balances), W1-11 (day reconciliation), W1-18 (stock card) and W1-20 (reports).

## Design

| Choice | Why |
|---|---|
| **A pure engine** in `packages/posting`: `postSale(sale, context, state) → { ok, posting: { entryDate, journal, movements, partyEntries, exceptions, state } } \| { ok: false, error }`. Context (settings): the role → account map, each payment method's account (ACC-08), the customer's terms, the lock date. State (derived): each item's cost (`avgCost`, tenant-wide `onHand`) and each location's balance; the posting returns the state it changed. It never throws for a business reason and never touches the database. Amounts use `@erp/domain`'s `Money`, `Qty`, `mulQty` and its one rounding rule (D-079). | Rule 2's pattern applied to posting: deterministic, golden-tested, and the same code runs live and in the rebuild, so they can't disagree. |
| **The sale entry** (posting rules §4.1), one journal entry per document, lines aggregated per account (and party): `Cr SALES` Σ `line_total`; `Dr SALES_DISCOUNT` `bill_discount`; `ROUNDING` `rounding` (positive = the customer paid more = Cr, negative = Dr); `Dr CASH_IN_TRANSIT` the cash payments (already net of change on the document); `Dr` each non-cash method's bank, wallet or card account; `Dr AR_CONTROL (party)` the on-account amount; `Cr TAX_PAYABLE` `tax_total` when it isn't 0 (never for Delux); `Dr COGS / Cr INVENTORY` Σ cost. Zero lines are left out. Memo = the bill number; every line carries the document's branch. | Exactly doc 04 §4.1. Per-item cost detail lives in the stock ledger, so the GL stays readable (two lines for cost, not one per item). |
| **Cost and the stock ledger** (INV-01, D-017): each sale line writes one `stock_movements` row out of its `location_id` (SHOP): `qty_delta` −qty, `unit_cost` = the item's current average, `value_delta` = −round(qty × avg), `avg_cost_after` (unchanged by a sale), `source_line_id` = the line. `stock_balances` (per item and location) and `item_costs.on_hand` (tenant-wide) move with it. **The line's cost lives only on its movement**: `sales_lines.unit_cost` is dropped, because finalized lines are never updated (rule 3) and a returned line (W1-13) reads its original cost from the movement. | Data model §7. Keeping the cost on the derived row keeps the document immutable and the cost rebuildable. |
| **Average cost** (INV-02): `item_costs` (data model §4: `avg_cost`, `on_hand`, `last_cost`, `last_supplier_id`, `last_receipt_at`). The receipt formula (`(on_hand × avg + qty × net_unit_cost) / (on_hand + qty)`, or `net_unit_cost` when on hand ≤ 0, rounded half away from zero) is built and golden-tested now as `averageAfterReceipt`; W1-14 (opening stock) and W1-16 (goods receipts) are its first callers. **An item with no known cost yet** (`avg_cost` null: never received, not in the opening stock) posts at cost 0 with a `no_cost` exception (owner answer 2). | Posting rules §5.1. The sale side and the receipt side share one cost state, so W1-16 only adds a document type. |
| **Negative stock** (INV-03): allowed always. A `negative_stock` exception (severity low) when a movement takes an item's balance at a location **from 0 or more to below 0**; further sales while it stays negative don't add more, the next crossing does. | The alert says "this went wrong here" once, instead of on every sale of an item that is already short. |
| **Customer and supplier ledgers** (ACC-03): `party_ledger_entries` (`role`, `entry_date`, `due_date`, `amount` + = owed more) and `party_balances` per party and role, both written only by the engine. A sale's on-account part writes `+amount` for the customer, due = business date + `payment_terms_days` (none = the same day). The writer serves both roles; the first supplier document is the goods receipt (W1-16). The counter can't sell on account until W1-09, so this path is golden- and integration-tested now through a document built in the test. | Data model §3. Ageing is FIFO at report time (W1-20), so no allocation table. |
| **Accounts by role** (ACC-01, ACC-08): the engine resolves every account through `accounts.system_role` and `payment_methods → bank_accounts.gl_account_id`, loaded once per posting. A method without an account gives the error `method_unmapped`. **Delux: Raast and bank transfer → HBL (1160)** (owner answer 1). **The mapping can change later:** the tenant setup now applies a payment method's bank account from the spec (the one setting meant to change; written to the audit log), so moving Raast to Soneri is an edit to `delux.json` and a re-run. Bills already posted stay on the bank they reached (rule 3); bills after the change go to the new one. Other differences stay reported, not applied (D-083). | The chart was validated at setup (W0-11); the engine just reads it. A back-office screen for payment methods can come with W1-19. |
| **Tax lines at 0%** (ACC-09): push now sets each line's `tax_code_id` to the item's code or the tenant's default (new `tax_codes.is_default`, one per tenant, set on Delux's `ZERO`), with `tax_amount` 0. The engine posts `TAX_PAYABLE` from `tax_total` and has a golden case at 17%, so switching tax on later is data, not schema. | "Tax lines on documents without schema changes": every line already says which code applied. |
| **Inside the push transaction** (architecture §5.2 step 4): after the document's rows are inserted, `postDocument(c, 'sale', id)` runs under a **savepoint**. Success → its rows are committed with the document. A posting error (`method_unmapped`, a sale on account without a customer, or an unexpected database error) → back to the savepoint, the **sale is still accepted** with a `posting_failed` exception (severity high, `details.code`), the error goes to Sentry and the log, and the push result is unchanged (`accepted`). | SYN-03: a completed sale is never refused, and one bad posting must not lose the bill. Architecture §11: posting errors must be 0 and alert. |
| **A bill whose figures don't add up** (accepted and flagged `document_inconsistent` since W1-07, D-094) **is posted, with the difference on *Posting suspense*** (new account 1190, role `SUSPENSE`, owner answer 3): the revenue, discount, rounding and tax lines come from the lines and amounts, the tender lines from the payments, the cost from the stock movements, and one `SUSPENSE` line (Dr or Cr) balances the entry. The accountant clears it with a journal voucher (W1-19). | The stock and the cash stay right; only the difference waits, where it is easy to find. |
| **Posting order** (D-017): `posting_state` (one row per tenant: the last posting seq and journal number) is locked `FOR UPDATE` at the start of each posting, so a tenant's postings run one at a time, in a recorded order. `postings` (`seq`, `source_type`, `source_id`, `posted_at`, `entry_date`, `context`), append-only and unique per source, is the **order of record**: the ledgers are derived from the documents plus this order. `context` keeps the settings the posting used (the accounts by role and by method, the lock date, the customer's terms), so a rebuild after Raast moves from HBL to Soneri still finds the old bills on HBL. Journal numbers come from the same row: `J` + 6 digits, per tenant. | Average cost depends on order; recording it makes a rebuild reproduce the live costs exactly. One shop's few hundred bills a day serialize in milliseconds; the lock is held only for the posting at the end of each document's transaction. |
| **Catch-up** (`postPending`): posts, in `received_at` order, every accepted document with no `postings` row. Runs in `apps/worker` every minute, and once on start-up, so **the bills already accepted on staging before W1-08** are posted (the W1-07 promise), and a bill held by `posting_failed` posts by itself once the cause is fixed (e.g. the owner maps Raast). It records the result on the open `posting_failed` exception (`details.postedAt`); the exception stays for review. | Rule 4: posting is derived, so posting later is the same function, just a later place in the order. |
| **Lock date** (posting rules §1.6): a document dated on or before `tenants.lock_date` posts on the day after it, keeps its own business date on the document, and raises `posted_after_lock`. Every ledger row of that posting uses the entry date. Fiscal periods are W1-19. | Delux's lock date is set at cutover (2026-12-31); late offline December bills must still post. |
| **Database guards** (rule 4): `journal_lines` `CHECK (debit >= 0 AND credit >= 0 AND (debit = 0) <> (credit = 0))`; a **deferred constraint trigger** refuses an entry whose debits ≠ credits at commit; `erp_app` may not `UPDATE` or `DELETE` `postings`, `journal_entries`, `journal_lines`, `stock_movements`, `party_ledger_entries`. The three balance tables (`stock_balances`, `party_balances`, `item_costs`) and `posting_state` are updated in place by the engine only. A repo test fails if any file outside `packages/posting` writes the ledger tables. | Invariants 1 and 2 of the posting rules, enforced by the database and a test, not only by review. |
| **Rebuild check** (ACC-02): `checkRebuild(tenant)` reads the documents and `postings` in one `REPEATABLE READ` snapshot, replays the pure engine in `postings.seq` order **in memory**, and compares the result with the stored ledgers and balances (ids and timestamps aside). It takes no locks and writes nothing, so it can run any time; `erp-tenant posting-check <env> <shop>` prints the differences and exits 1 on any. **Apply** (delete the derived rows and write the replay) is the same replay plus a write, as `erp_owner`, refused when any posting falls on or before the lock date, and audited. | Architecture §7: compare-only by default, an explicit step to rewrite. In memory, a check of a whole year is a read, not a lock on the shop. |
| **Tables (migration 0009):** `item_costs`, `stock_movements`, `stock_balances`, `party_ledger_entries`, `party_balances`, `journal_entries`, `journal_lines`, `postings`, `posting_state` as data model §4, §7, §9 (money `bigint`, quantity `numeric(14,3)`); exceptions gain `no_cost`, `posting_failed`, `posted_after_lock`; `tax_codes.is_default`; `sales_lines.unit_cost` dropped; `SUSPENSE` added to the `accounts.system_role` check. Every table: `tenant_id` + forced RLS (rule 5) and `enable_audit`; `stock_balances` and `party_balances` also `enable_sync` (the counter pulls customer balances in W1-09; a rebuild overwrites their rows, never deletes them); mirrored in `schema.ts`. | Data model, so W1-09 to W1-20 read the same shapes. |
| **Observability** (architecture §11): a span per posting with its duration; `posting_failed` logged as an error with the document, number and code (never the payload). The Grafana alert rule on it is the devops follow-up from W1-07. | "Posting errors (must be 0)" needs a signal before it needs a dashboard. |

## Scope

1. **`packages/posting`:** `accounts.ts` (role and method resolution), `cost.ts` (`averageAfterReceipt`, line cost), `sale.ts` (`postSale`), `replay.ts` (the in-memory state and `replay`), `db/post.ts` (`postDocument`, `postPending`), `db/rebuild.ts` (`checkRebuild`, `applyRebuild`); golden `post-sale.json`, `average.json`; property tests; package deps on `@erp/domain`, `@erp/db`, `pg`.
2. **`packages/domain`:** `SUSPENSE` in `SYSTEM_ROLES` and the required roles.
3. **`packages/db`:** migration `0009_posting.sql`, `schema.ts`, `retail-coa.json` (1190 *Posting suspense*), tenant setup (`tax_codes.is_default`, a `posting_state` row, a payment method's bank account applied from the spec and audited), `infra/db/tenants/*.json` (the default tax code; Delux's Raast and bank transfer → `hbl`). Re-running the Delux setup on staging and production adds 1190 and maps the two methods.
4. **`apps/api`:** push sets each line's `tax_code_id` and calls `postDocument` under a savepoint; `tenant-admin` gains `posting-check` and `posting-rebuild`, and `infra/db/bin/erp-tenant` the matching commands.
5. **`apps/worker`:** the `postPending` job (every minute and on start-up), across tenants.
6. **Docs:** new `docs/modules/accounting/spec.md` (the engine contract, order of record, failure path, rebuild); posting rules §1 (failed postings and the catch-up), §4.1 (no cost, suspense); data model §4 (`item_costs`), §5 (`unit_cost` on the movement), §7, §9 (`postings`, `posting_state`, built in W1-08), §10 (the new kinds); architecture §7 (order of record, the in-memory check); accounting and inventory READMEs; `docs/runbooks/` *A bill didn't post*; decision entry **D-095**.

**Out of scope:** returns, exchanges and the original-cost lookup (W1-13); voids and reversal entries (W1-12); cash handover and the automatic handover when `cash_handover_mode = off` (W1-10); customer balances on the counter and credit control (W1-09); goods receipts, supplier documents and the first real receipt average (W1-16); opening stock and balances (W1-14); fiscal periods and journal vouchers (W1-19); stock card, ledgers, trial balance and exception screens (W1-18, W1-20); pulling stock to the counter; a re-costing job (Phase 2, architecture §7).

- [x] **Sale entry (golden, `post-sale.json`):** the worked example (doc 04 §8: Rs 4,350 cash, cost 3,100) → exactly `Dr CASH_IN_TRANSIT 4,350 · Cr SALES 4,350 · Dr COGS 3,100 · Cr INVENTORY 3,100`; line and bill discounts; rounding up and down; split cash + JazzCash + card; two payments of one method aggregated; on account → AR line with the party and a customer ledger entry due after the terms; a 100%-discount bill; tax at 17% → a `TAX_PAYABLE` line; quantities in thousandths (1.500 m of hose) rounded half away from zero; an item without a cost → cost 0 and `no_cost`; a balance crossing below 0 → `negative_stock` once, already negative → none; dated on or before the lock date → the next day and `posted_after_lock`; Raast unmapped → `method_unmapped`; payments Rs 50 short of the total, and Rs 50 over → a `SUSPENSE` line of Rs 50 (Dr, then Cr) and the entry balances.
- [x] **Average (golden, `average.json`):** a receipt on positive stock re-averages with rounding; on zero and on negative stock takes the receipt cost; fractional quantities.
- [x] **Properties (`fast-check`):** any generated sale's entry balances, has no zero or two-sided lines, and its cost lines equal −Σ the movements' `value_delta`; replaying postings one by one equals replaying them together.
- [x] **Posting in push (integration):** an accepted bill has its entry, movements and balances in the same transaction, with the journal number and `postings` row; a re-push (`duplicate`) posts nothing twice; a Raast bill with Raast unmapped → `accepted` plus `posting_failed`, and nothing half-posted; two devices pushing the same item at once → both posted, costs in `postings` order; RLS keeps another tenant's ledgers out.
- [x] **Guards (integration):** an unbalanced entry inserted directly fails at commit; a two-sided or zero line fails; `erp_app` can't update or delete ledger rows; a repo test finds no ledger-table writes outside `packages/posting`.
- [x] **Catch-up (integration):** bills stored before posting (the W1-07 state) are posted in `received_at` order; after mapping Raast, the held bill posts and its exception notes it.
- [x] **Rebuild (integration):** 30 generated bills (mixed items, tenders, no-cost items, negative stock) pushed through the real route → `checkRebuild` finds no difference; one movement's cost changed as `erp_owner` → reported; `applyRebuild` restores it and is refused when a posting is on or before the lock date.

## Build notes (2026-10-31)

- **The push answer to the counter is unchanged.** The counter checks each answer against its fixed list of exception kinds, so a counter still on the old app would refuse an answer naming `no_cost` or `posting_failed` and retry forever. Posting exceptions are recorded on the server only; three assertions in `posting.int.test.ts` moved from the answer to the exceptions table.
- **Migrations can't touch tenant rows** (forced RLS on the owner role too), so existing tenants get 1190 *Posting suspense*, the default tax code (the spec's first) and the HBL mapping by re-running the tenant setup, now on the go-live checklist. The setup reports these under a new *updated* list.
- **The order of record keeps the context** (accounts by role and method, lock date, terms) on each `postings` row; without it, a rebuild after Raast moves from HBL to Soneri would move the old bills too. Tested.
- **No audit columns on the ledger tables:** the append-only ones carry `posted_at` and `posting_seq`; the balances carry `updated_at`. Who and when is on the document and in `postings`.
- **The push test tenant** now has the retail chart, a bank for Raast and a cost and shelf stock for its item (`seedChart`, a new test helper), so posting adds nothing to what those tests check; its `unit_cost: null` assertion went with the column.
- **The replay property test** computed `-0` for a sale with no costed item; it now subtracts from 0.
- **The worker** now connects as the app role (it already had `app.env`) and runs jobs on a small runner: start-up, then a minute after each run, never overlapping, a failing run reported to Sentry. It has unit tests; `postPending` itself is integration-tested.
- **`@erp/domain` exports `divRound`**, so the average uses the one rounding rule (D-079).

## Risks

| Risk | Mitigation |
|---|---|
| A posting bug stops bills being accepted | Posting runs under a savepoint: on any error the sale is still accepted and flagged, and the catch-up posts it after the fix. |
| The live ledgers and the rebuild drift apart (two code paths) | One pure engine for both; the database layer only loads context and writes; a rebuild check runs in the integration suite and on staging after each deploy. |
| Costs depend on arrival order across counters (D-017) | Accepted by D-017; the order is now recorded (`postings`), so it is at least reproducible. A re-costing job is Phase 2. |
| The tenant posting lock slows pushes | Held only for the posting at the end of each document's transaction; measured in Verify 2. A shop pushes at most a few bills a second. |
| Before opening stock (W1-14) every pilot sale is negative stock at cost 0 | Expected and flagged once per item; W1-14 loads the opening stock and costs. How pilot postings are cleared before cutover is decided with W1-14 and the go-live checklist, not here. |
| Rounding: Σ (on hand × avg) drifts from the `INVENTORY` balance by a few paisa | Half away from zero on every movement; the stock valuation report (W1-20) shows the difference, and an accountant's adjustment clears it. Recorded in the spec. |
| Four days with no slack | No screens; returns, voids and receipts stay in their own tasks. Built in the order engine → tables → push → catch-up → rebuild, so the pilot's must-have (bills posted) lands first. |

## Owner answers (2026-10-29)

1. **Raast and bank transfer go to HBL** for now. The mapping must be changeable later (e.g. to Soneri): the tenant setup applies it from the spec, and only bills after the change go to the new bank.
2. **An item sold before its cost is known posts at cost 0** and is flagged `no_cost`, as the migration does for items with no cost.
3. **A bill whose figures don't add up is posted**, with the difference on a new *Posting suspense* account (1190); the accountant clears it with a journal voucher.
4. **No screens in this task.** The owner checks it through the `posting:check` result and the trial balance recorded in this plan; the stock card and reports come in W1-18 and W1-20.
